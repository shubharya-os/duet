duet · open source · MIT

Two AI models build it.
The harness checks the rules.

A single agent grades its own homework and reports that it passed. duet puts a second model in the loop, runs your tests itself, and holds each workflow to a rule it checks against what actually happened — not what either model says happened.

Nine commands, each with a checked rule

Each one tells the pair its rule — and then checks it.

duet build "…"

Start from nothing. The gate is red before any code exists, and a gate already green on an empty directory is refused.

duet fix "…"

The tests are replayed against a snapshot of the original code. They must fail there and pass now.

duet add "…"

A test must fail against the code as it was before. A whitespace edit to a test file does not count.

duet refactor "…"

Every test that existed at the start must end byte-for-byte unchanged. Refused if the suite starts red.

duet plan "…"

Both argue it out into PLAN.md. Any other file changing clears both sign-offs.

duet review

A second model reads your diff, held read-only by its backend — not asked politely.

duet make "…" --like URL

Research the references from public sources, build, then score parity in the harness. It will not finish while the reference's name, domain or colours are still in the product.

duet jury

Simulated users, a paying client, an investor, judges and a skeptic. Every objection must quote the product, and the harness checks the quote is really there.

duet page check

A website's gate: renders the page in Chrome at desktop and phone widths and fails on what is wrong on screen.

What it cannot do

Two models can agree and still be wrong — one session ended in consensus on a CLI that crashed on Python 3.9, because the gate ran on 3.12 and the criteria never named a version. The gate only proves what it runs. fix cannot tell that a failure on the original code is this bug, and says so when the only failure is an import. Every one of these is written down, with the session that found it, in docs/QA.md.
